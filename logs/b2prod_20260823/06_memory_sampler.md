## Properties that carry the evidential weight

**Flushed and fsynced per record.** The run this exists for is the one the
OOM killer ends: SIGKILL, exit 137, no traceback, no summary. The last record
on disk names the phase it died in. A truncated tail is dropped, not
repaired, and a file with no trailer reads `INCOMPLETE` with the missing
checkpoints listed.

**It does not perturb what it measures.** The sampler takes scalars off the
arrays and keeps no reference — asserted with a `weakref` that must be dead
after `mark()` returns. And `detect_page(backend=None)` produces identical
detections with the observer attached and without.

**It counts the allocation, not the window.** `rec["patch"]` is a small
reshaped slice of a **full-bound 251,740 B copy** of the receive buffer
(`raw_patches.append(np.array(self._patch_rx_buf))`), so the whole copy lives
as long as the record — the whole page. Summing `patch.nbytes` under-reports
that several-fold. `retained_bytes()` reports both numbers so the gap is
visible: at the corpus maximum of 82 candidates it is ~19.7 MiB retained, and
it is the only page-level allocation that scales with candidate count rather
than page size.

## Verdicts

`PASS` (all checkpoints, no swap) / `HOLD` (any swap) / `INCOMPLETE` /
`NOT-A-GATE` (not read from `/proc`). Swap beats INCOMPLETE in precedence:
INCOMPLETE invites "re-run it", HOLD says the memory result itself is not
usable. `summarise()` recomputes the verdict from the records and is the
authority; the trailer is a convenience, and the runs that matter most do not
have one.

## Off-board shakedown — NOT-A-GATE by construction

Dev x86 Windows, Python 3.13.14, NumPy 2.5.1, cv2 5.0.0, PyMuPDF 1.28.0 /
MuPDF 1.29.0, `samples_mv=True`. `--backend cpu --debug-images off
--no-annotate --geometry-json`, i.e. the board's array configuration.
Three separate processes, one page each.

| run | page | baseline | peak | delta | candidates | segments |
|---|---|---|---|---|---|---|
| `06_sampler_offboard_dryrun.jsonl` | `doc_002` p1, 9792×6336 | 75,388 kB | 328,728 kB | **+253,340 kB = 247.4 MiB** | 44 | 63 vector |
| `06_sampler_offboard_dense.jsonl` | `doc_006` p1, 9792×6336, 3,258 drawings | 75,468 kB | 329,084 kB | **+253,616 kB = 247.7 MiB** | 80 | 91 vector |
| `06_sampler_offboard_smallpage.jsonl` | `doc_035` p1, 4896×3168, 3,654 drawings | 75,200 kB | 145,136 kB | **+69,936 kB = 68.3 MiB** | 0 | 42 vector |

Report: `06_sampler_offboard_dryrun.txt`.

Four things this already says:

1. **The renderer is the whole peak.** `VmHWM` reaches its final value at
   `render_complete` on all three pages and no later phase adds to it. The
   predicted arrays inside `render_page` are 186,126,336 + 62,042,112 =
   248,168,448 B = 236.7 MiB; measured process delta is 247.4 MiB. The
   ~10.7 MiB gap is the 8 MiB conversion stripe plus allocator slack, so the
   docstring's "~248 MB" is corroborated rather than merely restated.
2. **Steady state is 177.5 MiB** across binarise→match: grey + `page_bin` +
   `clean_bin`, 62,042,112 B each, and `alias_groups` confirms they are
   **three distinct allocations** on the CPU path — the suppression copy is
   really there. On `pl-extract`/`pl-all` this should drop to two groups;
   that is now a measurement, not an inference from the backend name.
3. **Path density did not move the peak.** The 3,258-drawing page peaked
   276 kB above the sparse one. The `get_drawings()` excursion I flagged is
   not present at this corpus's density. Stated precisely: what this bounds
   is only "did not exceed the render peak" — which leaves ~65 MiB of blind
   spot, because `VmHWM` is monotonic. That is why
   `--mem-sampler-per-phase-peak` was added (resets `VmHWM` via
   `/proc/self/clear_refs` after each record, needs
   `CONFIG_PROC_PAGE_MONITOR`, and says `"run"` in the records when it is
   unavailable rather than claiming per-phase).
4. **Peak tracks page area**, 3.62× for 4× the pixels.

**Do not carry the 321 MiB total to the board.** The board's interpreter
baseline is a different number (32-bit, Python 3.10.4, NumPy 1.21.5). The
figure that transfers is the **+247.4 MiB delta**, and against ~290 MiB of
userspace that is the entire margin — which makes the renderer, not the
matcher, the thing that decides whether Stage 2 fits.

## Corpus facts found while picking the gate pages

The maximum-dimension page and the most path-dense page are **different
PDFs**, so the memory gate needs both:

* largest / most candidates: `doc_003` p1, 9792×6336, 68
  candidates (the Stage 3 page);
* densest full-size: `doc_006` p1, 3,258 drawings, **80
  candidates** — over the 64-descriptor limit, so two extractor batches;
* densest overall is the **smallest** page: `doc_035` p1,
  4896×3168 with 3,654 drawings. It doubles as the small-page
  re-invocation.

(Drawing counts are `len(page.get_drawings())`, i.e. drawing dicts, not path
items.)

## Also in this change

`HAVE_SAMPLES_MV`'s comment said `Pixmap.samples_mv` arrived in "1.19.5+".
It is **1.18.17+**. The `hasattr` guard is what decides, so nothing behaved
wrongly — but the wrong number mattered once a board-native 1.19.2 became the
candidate runtime, because it made a zero-copy build look like a fallback
build. Corrected in place.

`process_pdf` now records the geometry file's **own size on disk** rather
than `len(payload)`: text mode translates newlines, so on Windows the encoded
string is 415 B shorter than the file on a 40-detection page.

## What this does not establish

Nothing about the board. Every number here comes from Windows `psapi`
working-set counters, which is why every record reads `NOT-A-GATE`. The
instrument is proven; the measurement is not made until `fitz` exists on the
board and the three runs above are repeated there under `/proc`.
